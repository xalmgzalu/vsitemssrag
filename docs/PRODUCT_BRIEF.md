# Продуктовый бриф VistaSport RAG

Версия: **8 ноября 2026**. Точка входа для агента в роли Product Owner.

Связанные документы продуктового контура:

- [PRODUCT_VISION.md](PRODUCT_VISION.md) — долгосрочное видение, персоны, позиционирование и дорожная карта фаз.
- [SPRINT_1_BACKLOG.md](SPRINT_1_BACKLOG.md) — актуальный инженерный бэклог с задачами P0/P1 и критериями приёмки для Codex.

Документ собран по существующему коду, сценариям и результатам экспериментов.
Он различает факты проекта и рабочие продуктовые гипотезы. Согласованный план Этапа 1 и перехода к Telegram после гейта качества
зафиксирован в PRODUCT_VISION.md и SPRINT_1_BACKLOG.md. Гипотезы аудитории
и коммерческого эффекта требуют отдельной проверки.

## Цель

Рабочая формулировка: помочь игроку выбрать основание для настольного тенниса
из каталога VistaSport под уровень, стиль и бюджет, объяснив выбор проверяемыми
данными и обозначив недостаток информации.

Полезный результат для пользователя — небольшой список подходящих вариантов
со ссылками, ценами и понятными причинами выбора либо конкретное объяснение,
почему данных или подходящих товаров недостаточно.

## Что известно и что предполагается

| Область | Статус | Контекст |
|---|---|---|
| Предмет подбора | Подтверждено реализацией | Основания из каталога VistaSport; интерфейс и ответы на русском |
| Ограничения пользователя | Подтверждено сценариями | Бюджет, уровень, стиль, материал и желаемые ощущения |
| Доверие к ответу | Подтверждено правилами и аудитом | Нельзя выдумывать свойства, совместимость, цены или сравнивать разные брендовые шкалы как одну |
| Источники | Подтверждено реализацией | Каталог — основа; ограниченные агрегаты отзывов — опциональный эксперимент |
| Основная аудитория | Гипотеза | Новички и любители, которым сложно выбрать основание по карточкам товаров |
| Проблема выбора | Гипотеза | Характеристики трудно сопоставлять, субъективные ощущения смешиваются с фактами, ассортимент велик |
| Интерфейсы | Факт текущей реализации | CLI и локально запущенный Telegram-бот с кнопками товаров и оценками 👍/👎 |
| Бизнес-эффект | Не определён | Не согласованы монетизация, конверсия, коммерческий заказчик и модель эксплуатации |

Интервью и исследование аудитории в репозитории не зафиксированы. Продуктовые
гипотезы нельзя представлять как подтверждённые пользовательские потребности.

## Текущие границы и предлагаемый MVP

Фактический прототип: CLI и локально запущенный Telegram-бот с общим сервисом
подбора, PostgreSQL, semantic search и ответом Gemini. Рабочее предложение для ближайшего MVP — надёжный подбор
оснований на пяти имеющихся сценариях с ручной оценкой качества.

В ближайший объём входят:

- подбор из доступного каталога с учётом явного бюджета и критериев запроса;
- один уточняющий вопрос вместо случайного выбора при общем запросе;
- до трёх вариантов с ценой, источником и объяснением по доступным данным;
- честный ответ при отсутствии подходящих товаров или подтверждения свойства;
- проверка качества и воспроизводимые эксперименты с отзывами.

Этап 1 принят PO. TASK-3 (Telegram) реализован после подтверждения гейта v6.
TASK-3.1 исправил вёрстку; TASK-3.2 добавил реренкинг и справку материалов.
Для новой комбинации retrieval/prompt подготовлен v7, полный прогон и новый
аудит ещё не выполнены. Далее по бэклогу — сбор накладок. Веб-интерфейс, память диалога, комплекты
ракеток, другие магазины, корзина, оплата и массовый сбор отзывов пока не
реализованы. Остальные фазы описаны в PRODUCT_VISION.md. Работающий CLI
не является доказательством готовности сервиса для конечного пользователя.

## Ожидаемое поведение

Это критерии желаемого результата, а не утверждение, что всё уже реализовано.

| Ситуация | Ожидаемое поведение и критерий приёмки |
|---|---|
| «Посоветуй хорошее основание» | Один вопрос об уровне, стиле и бюджете; без списка товаров до уточнения |
| Новичок, бюджет до 6000 ₽ | Все рекомендованные товары имеют известную цену не выше 6000 ₽; пригодность не выводится только из класса ALL/OFF- |
| Нет вариантов в бюджете | Явно сообщить об отсутствии найденных подходящих вариантов; не подменять их рекомендациями дороже бюджета |
| Быстрое карбоновое основание | У выбранных товаров есть прямое подтверждение композитной конструкции; нет общего рейтинга скорости из разных брендовых шкал |
| Защита с длинными шипами | Защитный тип обоснован каталогом; опыт использования с шипами рассматривается отдельно, без обещания совместимости |
| Мягкий inner carbon | Конструкция и субъективное чувство разделены; мягкость не выводится только из внутреннего композита или толщины |
| Использованы отзывы | Число, знаменатель, товар и смысл сигнала соответствуют источнику; упоминание не превращается в доказанную пригодность |
| Недостаточно данных | Прямое признание ограничения без выдуманных характеристик и уверенных выводов |
| Генератор не прошёл проверки | После повторов используется проверенный каталоговый fallback; если он тоже отклонён, CLI возвращает ошибку, бот — понятное сообщение без внутренних деталей |

Текущий CLI не хранит историю: после уточняющего вопроса пользователь должен
сформулировать следующий запрос самостоятельно со всеми нужными критериями.

## Как оценивать успех

Уже зафиксированный порог расширения enrichment: не менее **12 из 15**
enriched-ответов по строгому ручному аудиту и **ноль** ошибок чисел evidence
или неподтверждённых заявлений о совместимости. В полном v6 порог достигнут по аудиту агента-разработчика: 13/15 enriched,
88 evidence-фраз без ошибок и ноль обещаний совместимости. Это результат прежней
версии retrieval/prompt; полный v7 ещё не проверен. Это не независимый
или человеческий аудит; оставшиеся сравнительные формулировки перечислены в
[AB_V6_AUDIT.md](AB_V6_AUDIT.md).

Это внутренний порог качества эксперимента, а не критерий product-market fit
или полной готовности к запуску. Автоматический grader используется для
регрессий и диагностики; неполный прогон с высоким pass rate не считается
успешным экспериментом. Аудит должен проверять все продуктовые утверждения.

Предлагаемые продуктовые метрики для будущего пилота: доля сессий, где игрок
считает подбор полезным; доля запросов с соблюдёнными жёсткими ограничениями;
доля объяснений, подтверждённых источниками; частота отказов генерации;
время и стоимость получения ответа. Целевые ориентиры зафиксированы в PRODUCT_VISION.md;
👍/👎 уже сохраняются в локальной SQLite, но объём пользовательской выборки,
метод измерения затрат/задержки и критерии анализа пилота ещё не определены. Переход по ссылке на товар сам по себе не доказывает
правильность рекомендации.

## Открытые решения для владельца продукта

1. Для кого первая версия: новичок, опытный любитель или консультант магазина?
2. Где разместить бота постоянно и кому предоставить доступ к уже запущенному локальному пилоту?
3. Подбор ограничивается основаниями VistaSport или нужен другой ассортимент?
4. Должен ли сервис вести многошаговый диалог и помнить предыдущие ответы?
5. Какой результат первого пилота считается полезным и как собрать обратную связь?
6. Какие допустимы задержка, стоимость запроса и частота обновления каталога?
7. Кто принимает результаты ручного аудита и решение о запуске?

Эти вопросы не блокируют исправление текущих ошибок бюджета и evidence.
При подготовке новых функций агент должен обозначить зависимые предположения,
а не принимать открытые решения за владельца.

## Как войти в проект другому агенту

1. Прочитать этот бриф: цель, рамки, гипотезы и ожидаемое поведение.
2. Прочитать [CURRENT_STATE.md](CURRENT_STATE.md): реализованное, ограничения,
   состояние экспериментов и следующий технический шаг.
3. При детализации задач использовать [архитектуру](project_info.md),
   [разбор экспериментов](ENRICHMENT_EXPERIMENT.md),
   [инструкции eval](../evals/README.md) и `evals/rag_cases.json`.
4. Проверить `git status -sb`, `git log -5 --oneline` и локальные unit-тесты.
5. Составить backlog с пользовательским результатом, критериями приёмки,
   зависимостями и отметками «факт / гипотеза / решение владельца».

Код и документация версионируются. `.env`, каталог и сырые JSON-checkpoint в
`data/exports/` исключены из Git: новый клон не содержит ключей и результатов
старых генераций. Сводки сохранены в документации. Без локальных файлов можно
изучить проект и запустить unit-тесты; воспроизведение эксперимента требует
доступа к БД, API и соответствующему evidence-набору. Если исходных файлов нет,
это новый сбор и новый эксперимент, а не продолжение исторических v5/v6.
