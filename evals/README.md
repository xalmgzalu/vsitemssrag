# Проверка RAG и A/B-эксперименты

Актуализировано **7 ноября 2026** по коду и локальным checkpoint от 30 августа.

`rag_cases.json` содержит пять сценариев: новичок с бюджетом, быстрый composite,
защита с длинными шипами, мягкий inner carbon и общий запрос без критериев.
Для ручной проверки запускайте `ask` и оценивайте ответ по полю `review`:

```bash
uv run vsitemssrag ask "Я новичок, бюджет до 6000 ₽, хочу контрольное основание"
```

Добавляйте реальные формулировки пользователей отдельными кейсами. Проверки
не должны фиксировать ответ слово в слово, кроме детерминированного уточнения.

## Текущий протокол

`enrichment_ab_protocol.json` фиксирует `community_evidence_pilot_v4`: одинаковый
retrieval, модель, system instruction, 6 товаров, `temperature=0`, 3 повтора
для каждого из 5 сценариев в baseline и enriched. Различие условий — наличие
агрегатов отзывов для `matched`-товаров. Запланировано 30 ответов; общий запрос
обрабатывается детерминированно и не вызывает Gemini для генерации.

`vsitemssrag.rag.evaluation` содержит grader версии 3, а
`vsitemssrag.rag.validation` — валидатор версии 2. Проверяются ограничения
сценария, ссылки (в том числе сгруппированные), числовые агрегаты в привязке
к товару и сигналу, некоторые неподтверждённые сравнения и выводы.
LLM-as-a-judge не используется. Эти лексические проверки не оценивают все
фактические утверждения, поэтому после полного прогона нужен строгий ручной
аудит.

## Продолжение v4

Команда использует `.env` с `GEMINI_API_KEY` и `DATABASE_URL`. Новый прогон
выполняет retrieval до генераций; соединение с БД не простаивает во время
генераций. Между генерациями и исправляющими попытками выдерживается пауза
15 секунд. Временные ошибки API повторяются.

```bash
uv run python evals/run_enrichment_ab.py
```

По умолчанию:

- Evidence: `data/exports/review_enrichment_pilot_v2.json`.
- Output/checkpoint: `data/exports/enrichment_ab_results_v4.json`.
- Протокол: `evals/enrichment_ab_protocol.json`.

При совпадении конфигурации повтор команды продолжает checkpoint, пропуская
сохранённые ответы. Проверяются модель, параметры, версии grader/валидатора,
хеши prompt, протокола, кейсов и evidence. При несовпадении runner отказывается
продолжать. Не пересоздавайте evidence перед продолжением: изменится его хеш.

Последнее сохранённое состояние v4 — `paused`, 7 из 30 ответов. Причина:
«числовая evidence-фраза должна содержать один товар, один сигнал и одну пару
N из M». Простое продолжение не гарантирует устранения этой ошибки. Общий
advisor делает до трёх попыток получить прошедший validation ответ; при
исчерпании попыток runner сохраняет `last_error` и завершает работу с кодом 1.
Отклонённый ответ в checkpoint не записывается.

`--restart` начинает прогон заново и перезаписывает выбранный output. Для
изменённого поведения создайте новую версию протокола и отдельный output,
чтобы сохранить v4. Например, после подготовки `enrichment_ab_protocol_v5.json`:

```bash
uv run python evals/run_enrichment_ab.py \
  --protocol evals/enrichment_ab_protocol_v5.json \
  --output data/exports/enrichment_ab_results_v5.json
```

Файл протокола v5 пока не создан. Не смешивайте ответы разных версий в одном
checkpoint; `--case ID` подходит для диагностики, но не заменяет полный прогон.

## Пересчёт без новых генераций

Пересчёт сохранённых ответов v4 текущим grader, без Gemini и БД:

```bash
uv run python evals/regrade_enrichment_ab.py \
  --input data/exports/enrichment_ab_results_v4.json \
  --evidence-file data/exports/review_enrichment_pilot_v2.json \
  --output data/exports/enrichment_ab_results_v4_regraded.json
```

Передавайте evidence именно из конфигурации исходного прогона. Значения по
умолчанию у regrade относятся к **исходному** эксперименту: файлам
`enrichment_ab_results.json`, `review_enrichment_pilot.json` и
`enrichment_ab_results_regraded.json`. Новые проверки могут изменить оценки;
пересчёт не заполняет недостающие ответы и не завершает приостановленный прогон.

## Результаты и критерий готовности

Исходный эксперимент: после post-hoc исправления grader — 7/15 baseline и
12/15 enriched, но строгий ручной аудит — только 1/15 и 5/15. Завершённый v2
сохранил по 11/15 автоматически для обоих условий. v3 и v4 приостановлены;
высокая доля pass среди сохранённых ответов не является итогом эксперимента.

Порог расширения enrichment: не менее 12/15 enriched по строгому аудиту,
ноль ошибок чисел evidence и неподтверждённых заявлений о совместимости.
Достижение порога не подтверждено. Подробный разбор — в
[ENRICHMENT_EXPERIMENT.md](../docs/ENRICHMENT_EXPERIMENT.md), текущие задачи — в
[CURRENT_STATE.md](../docs/CURRENT_STATE.md).
